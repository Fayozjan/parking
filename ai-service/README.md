# ai-service

Python-микросервис: номер + сторона транспорта (передом/задом) по одному кадру.
Node-сервер вызывает его по HTTP (`server/utils/aiPlate.js`).

| Модель | Что делает | Откуда |
|--------|-----------|--------|
| `models/plate_side.onnx` | YOLOv8n: bbox номера + класс `plate_front` / `plate_rear` | обучается своими кадрами (`train/`) |
| `cct-s-v1-global-model` | OCR текста номера | `fast-plate-ocr`, качается сам при первом старте |

## Запуск

**Linux-сервер (PM2), один раз:**

```bash
bash ai-service/setup.sh                       # venv, зависимости, предзагрузка OCR-модели (нужны python3-venv и интернет)
pm2 start ecosystem.config.cjs                 # Node-сервер + AI
#   или только AI, если Node уже под PM2 с другим именем:
pm2 start ecosystem.config.cjs --only onbase-ai
pm2 save && pm2 startup                        # автозапуск после перезагрузки
curl http://127.0.0.1:8000/health              # проверка
```

PM2 перезапускает AI при падении (с нарастающей паузой) и по лимиту памяти 1.5 ГБ; логи — `pm2 logs onbase-ai`.
Порядок запуска неважен: пока AI не поднялся (~10 с на загрузку моделей), Node работает только по данным камеры.
Модель детектора `models/plate_side.onnx` лежит в git (12 МБ), поэтому едет на сервер вместе с кодом.
После обновления модели: `git pull && pm2 restart onbase-ai`.

**Windows (разработка):** `run.bat` (нужен готовый `.venv`: `python -m venv .venv`, затем `.venv\Scripts\pip install -r requirements.txt`).

Docker: `docker build -t onbase-ai . && docker run -p 127.0.0.1:8000:8000 onbase-ai`.
Без `models/plate_side.onnx` сервис не стартует.

```
POST /recognize   multipart image=<jpeg>
→ { "found": true, "plate": "01A123BC", "plate_confidence": 0.93,
    "side": "front", "side_confidence": 0.88, "bbox": [x1,y1,x2,y2], "detections": 1 }
GET  /health
```

`side`: `front` = машина едет на камеру (`forward`), `rear` = от камеры (`reverse`).

## Интеграция с проектом

Сервис вызывается из Node только по `AI_SERVICE_URL` (`server/.env`, по умолчанию `http://127.0.0.1:8000`).

1. **Горячий путь не изменился.** Событие камеры сохраняется по её данным, камера получает ответ сразу.
   AI синхронно вызывается только если камера вообще не прислала номер или направление (иначе нечего сохранять).
2. **После ответа камере**, в фоне (`anprVerification.service.js`, очередь на 2 запроса, не более 100 в ожидании):
   кадр уходит в AI, камера и AI голосуют (`utils/plateConsensus.js`).
3. **Номер** — совпали: берём, рейтинг +10. Разошлись — судьи по порядку: формат номера → известный номер из БД
   (белый список или проезды за 90 дней) → отрыв по уверенности не меньше 15 → иначе конфликт
   (остаётся номер камеры, `plate_conflict = true`). Слабое чтение AI (уверенность < 50) с камерой не спорит.
   Исправленный проезд хранит исходный номер в `plate_original`.
4. **Направление (въезд/выезд)** — события НЕ фильтруются: принимается каждое. Камеры ворот работают командой (см. `docs/api-endpoints.md`).
   На приёме направление берётся по движению, которое сообщила камера (`utils/passDirection.js`): едет на камеру (`forward`) —
   направление камеры, от камеры (`reverse`) — обратное (камера входа видит уезжающую машину → выезд, камера выхода видит
   въезжающую → въезд). Движение не сообщено — принимается направление камеры (`direction_source = default`).
   Затем в фоне AI голосует: если он уверен (сторона ≥ 0.7) и спорит с камерой, направление переворачивается
   (`direction_original`, `direction_source = ai`). Выключить переворот: `AI_DIRECTION_FLIP=false`.
   - Манёвр (машина только что проехала и сдаёт назад) проездом не считается (`skip_reason = maneuver`).
   - Одну машину, зафиксированную обеими камерами ворот в окне `coop_window_sec`, не дублируем: на приёме второе событие
     пропускается, а после переворота лишняя запись удаляется; оставшаяся получает подтверждение (`gate_confirmed`).
   - Камера записала проезд против своего направления (`inferred = true`) — помощь партнёру; подтверждение партнёром снимает пометку.
   - Выезд без въезда (или повторный въезд) в истории номера помечается `history_conflict`, проезд при этом не теряется.
5. Сервис упал или тормозит: таймаут 3 с, после 5 сбоев подряд пауза 60 с, проезд остаётся как записала камера.

Ограничение: Telegram-уведомление уходит при создании проезда и исправленный номер уже не заменит.

Тесты: `cd server && node --test utils/plateConsensus.test.mjs modules/anprCameras/anprVerification.test.mjs`.

## Обучение модели

Всё из каталога `ai-service`, в venv (`pip install open-image-models[onnx] opencv-python-headless`).

1. Положить реальные фото с камер в `dataset/inbox/` (любые вложенные папки; нужны разные машины, время суток, погода).
   Из БД выгружать не стоит, если там тестовые данные: `export_dataset.mjs` кладёт кадры в `dataset/raw`, оттуда их можно скопировать в inbox.
2. Предразметка (рамки готовой моделью, дубли отбрасываются): `python train/prelabel.py` → `dataset/prelabeled`.
3. Разметка стороны: `python train/labeler.py` → браузер, клавиши ← спереди, → сзади, ↓ пропустить.
   Прогресс сохраняется в `dataset/labels.json`. Нужно ≥100 кадров на класс (лучше 300+).
4. Сборка датасета: `python train/labeler.py --build` → `dataset/yolo` (train/val 80/20 блоками подряд идущих кадров).
5. `pip install -r requirements-train.txt && python train/train.py --epochs 80` (GPU: `--device 0`).
6. Готовая модель сама ложится в `models/plate_side.onnx`, сервис перезапустить.

## Переменные окружения

`DETECTOR_MODEL_PATH`, `OCR_MODEL`, `CLASS_NAMES`, `DETECTOR_CONF` (0.35), `DETECTOR_IOU` (0.5),
`CROP_PADDING` (0.0), `MAX_IMAGE_MB` (10).

## Качество (модель v2 от 2026-10-09)

Проверка на 270 кадрах val (148 спереди, 122 сзади; камеры те же, что в обучении). v2 — дообучение v1 на ~1400 кадрах,
из них ~630 «сзади»; v1 хранится в `models/plate_side_v1.onnx`.

| | v1 | v2 |
|---|---|---|
| Сторона верна, всего | 94.1% | **99.3%** |
| Спереди | 98.6% | 100% |
| Сзади | 88.5% | **98.4%** |
| Время на кадр (CPU) | ~51 мс | ~53 мс |

### Чтение номера

Эталон: 245 номеров, размеченных вручную (`train/plate_text_labeler.py`), кадры 1600 px с камер. Полный путь
(оригинал → детектор → OCR), `python train/ocr_eval.py` сравнивает модели и стратегии.

| Вариант | Номер целиком верен |
|---|---|
| `cct-s-v2` как есть (старый вариант) | 49.8% |
| + декодирование по формату (`app/plate_format.py`) | 74.3% |
| `cct-s-v1` + формат + отступ кропа 0 (**текущий**) | **94.3%** (полный путь, ~110–180 мс/кадр) |

Что дало выигрыш: (1) на позиции цифры выбирается лучшая цифра, на позиции буквы лучшая буква (`0→G`, `5→S`
были главными ошибками); (2) код региона проверяется по списку; (3) OCR обучен на тугих кропах, отступ 0.1 и больше
сильно вредит. MobileViT-модели для узбекских номеров не подходят (5–15%).

Уверенность `plate_confidence` надёжна: при пороге 0.5 берётся 90% кадров, из них верно 98.6%; при 0.9 берётся 77%, верно 99.5%.
`aiPlate.js` отдаёт её в Node как 0–100, поэтому порог `min_confidence` камеры автоматически отсекает сомнительные номера.
Номер от камеры по-прежнему приоритетнее: AI подставляется, только если камера номер не прислала.

Форматы номеров (`app/plate_format.py`): `A` `50A123BC` (физлица), `B` `50123ABC` (юрлица), `C` `01M017910`
(совместные предприятия, зелёный номер). Шаблон `C` длиной 9 знаков выбирается, только если сама модель выдаёт 9 символов:
без этого правила он перетягивал обычные номера с буквами `OO` (модель путает `O` и `0`). Запасное чтение «как есть» для
неизвестных форматов пробовали: оно портило верные номера (93.5% → 89.0%), откатили. Иностранные номера под эти шаблоны
не подходят и получают низкую уверенность, порог их отсекает.

Ограничения: эталон с тех же камер и всего один зелёный номер, поэтому надёжность шаблона `C` проверена слабо;
такие номера (и такси, дипломатические и т.п.) стоит добавить в эталон.
